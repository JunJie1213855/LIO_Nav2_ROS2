# RRT Exploration

Given a dynamic global map and the locations of multiple robots within the map, this package issues navigation goals to each robot in order to collaboratively explore the environment.

This is a ROS2 port of the RRT exploration algorithm in SMMR Explore repository https://github.com/efc-robot/SMMR-Explore. Several parts have been optimised for performance and memory handling.

> **Quickstart (single robot, TurtleBot3 + Nav2 + slam_toolbox):** see [docs/quickstart.md](docs/quickstart.md) for the exact commands and the full list of integration fixes.

## Dependencies
* ROS2

>  This package has been tested on ROS2 Humble, Ubuntu 22.04

**Compiling**
```bash
colcon build --packages-select rrt_explore --symlink-install
source install/setup.bash
```

**Running Exploration (single robot, root-namespace stack)**
```bash
# 1. Start the stack (Gazebo world, Nav2, slam_toolbox, RViz) at the root namespace.
#    Nav2 MUST be launched with the exploration params file so the planner can route
#    through unknown space:
ros2 launch nav2_bringup navigation_launch.py use_sim_time:=True \
  params_file:=<workspace>/src/rrt-explore/config/nav2_params_explore.yaml

# 2. Start the RRT node. The node REQUIRES a robot<ID> namespace (it extracts its
#    robot id from the namespace):
ros2 launch rrt_explore rrt.launch.py namespace:=robot1

# 3. Start / stop exploration:
ros2 topic pub --once /robot1/rrt/enable std_msgs/msg/Bool "{data: true}"
```

> **Note:** In the single-robot integration the node subscribes to the root-namespace
> topics (`/map`, `/global_costmap/costmap`, `/tf`, `/tf_static`) and sends goals to
> the root Nav2 action server (`/navigate_to_pose`). This is achieved by the absolute
> topics in `config/params.yaml`, the topic/action remaps in `launch/rrt.launch.py`,
> and the hardcoded absolute action name in `rrt.cpp`. Do NOT remove the `namespace:=`
> argument — without it the node fails with `Cannot extract robot id from node namespace {/}`.

**Multi-robot usage:** The rrt nodes should be run on all robots in the system. `<robot_namespace>`
should be replaced by the namespace of the respective robot for each instance (e.g. `robot1`,
`robot2`, ...). Multi-robot setups need a merged map and namespaced TF frames as described
in the upstream SMMR-Explore project.

### Subscribed Topics

| Topic | msg Type | Description |
| --- | --- | --- |
| `/rrt/enable` (resolved to `/<ns>/rrt/enable`) | std_msgs/msg/Bool | Send Command to Start / Stop RRT Exploration |
| `map_topic` (`/map` in this integration) | nav_msgs/msg/OccupancyGrid | Merged map of all robot local maps (realtime) |
| `costmap_topic` (`/global_costmap/costmap`) | nav_msgs/msg/OccupancyGrid | Global costmap generated by the navigation stack |
| `/tf`, `/tf_static` (remapped to root in this integration) | tf2_msgs/msg/TFMessage | TF topics. TF should include the transform between the map frame and the robot base frames (e.g. `map` ↔ `base_footprint`) |

### Published Topics

| Topic | msg Type | Description |
| --- | --- | --- |
| `/<robot_namespace>/frontier_targets` | visualization_msgs/msg/Marker | Detected frontier points by RRT |
| `/<robot_namespace>/rrt_segments` | visualization_msgs/msg/Marker | RRT visualization (tree) |
| `/<robot_namespace>/end_detection_frontiers` | visualization_msgs/msg/Marker | Remaining frontiers (Discovered via full map grid search. Only used for visualization and exploration completion detection.) |
| `/exploration_state` | rrt_explore/msg/ExplorationState | Exploration state |

### Parameters (`config/params.yaml`)

| Parameter | Value in this integration | Description |
| --- | --- | --- |
| `map_topic` | `/map` | Merged map topic (absolute, root namespace) |
| `costmap_topic` | `/global_costmap/costmap` | Planner server costmap topic (absolute, root namespace) |
| `robot_base_frame` | `base_footprint` | Base frame of the robot, excluding the namespace |
| `robot_frame_prefix` | `robot` | Robot namespace prefix. Namespaces must be `robot<ID>` (e.g. `robot1`, `robot2`) |
| `rate` | 100.0 | Exploration goal generation rate in Hz |
| `robot_count` | 1 | Number of robots in the system. Minimum 1 |
| `info_radius` | 1.0 | Info gain radius |
| `costmap_pixel_threshold` | **100.0** (was 30.0) | Frontier pruning threshold. Raised so frontier cells near walls (cost 99 in the inflated costmap) are kept; each dispatched goal is snapped to a nearby free cell by the node |
| `eta` | 1.0 | RRT steering step |
| `hysteresis_radius` | 3.0 | Hysteresis radius |
| `hysteresis_gain` | 2.0 | Hysteresis gain |
| `use_sim_time` | true | Use the simulation clock |

## Integration notes (single robot, root-namespace Nav2 + slam_toolbox)

The following were required to make the robot actually move with the standard
TurtleBot3 + Nav2 + slam_toolbox stack. Full details in [docs/quickstart.md](docs/quickstart.md):

1. **Namespace requirement** — the node must run under `robot<ID>`; it extracts its robot id
   from its own node namespace.
2. **Action client** — the client name is hardcoded to `/navigate_to_pose` (a bare-name
   remapping rule does not apply to action clients, so the client would otherwise stay on
   `/<ns>/navigate_to_pose` and reach no server).
3. **Goal snapping** — the raw frontier point lies in unknown space; the goal is snapped to
   the nearest free cell so Nav2 can reach it.
4. **Nav2 must plan through unknown space** — launch Nav2 with `track_unknown_space: false`
   (see `nav2_params_explore.yaml`), otherwise the planner cannot route to frontier goals.
5. **Frontier filters** — `find_frontiers()` and the frontier-pruning threshold were relaxed
   (only cost >= 100 drops a frontier) so wall-adjacent frontiers survive the costmap's
   inflation layer.
